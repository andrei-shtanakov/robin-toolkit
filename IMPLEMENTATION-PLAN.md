# План реализации Robin — AI chief of staff команды

> Рабочий план реализации бота по [ROBIN-SPEC.md](ROBIN-SPEC.md) под задачи проекта:
> круглосуточный Telegram-бот (+ голос), понимающий состояние проекта, проводящий
> онбординг сотрудников и интервью (по ТЗ/спецификациям и с кандидатами), размещённый на VDS.
>
> Статус: черновик v0.1 (7 июля 2026). Резолюция слотов согласована с заказчиком.

## 0. Что уже есть в репозитории (отправная точка)

| Артефакт | Что это | Готовность |
|---|---|---|
| `ROBIN-SPEC.md` | Stack-agnostic спецификация агента (§1–9 + реестр слотов). Это **контракт**, а не код. | Есть, v0.6 |
| `.claude/skills/*` | Скилы подготовки: `init-team-os`, `init-team-brain`, `init-team-decisions`, `robin-init`, `kb-*`. Строят базу знаний и конфигурируют спеку — **но не Robin**. | Есть |
| `template/` | Карта структуры базы знаний (`now.md`, `product/`, `decisions.md`, `skills/`). Заглушки. | Есть |

**Ключевой вывод:** реализации бота нет вообще — ни runtime, ни Telegram-адаптера, ни `soul.md`/`robin/duties.md` под эту команду, ни наполненной базы знаний. Репо даёт архитектурный каркас и инструменты подготовки. По правилу из README — «Files → skill. Running process → spec» — Robin ставится как **отдельный работающий процесс на нашем стеке по спеке**, а не копированием шаблона.

**Критично (порядок из README «The order matters»):** Robin без наполненной базы знаний — это просто чат-бот. Сначала строим базу знаний (шаг 1 тулкита), доказываем ценность одним реальным ответом, и только потом наращиваем обязанности. Онбординг и интервью **паразитируют на качестве базы знаний** — если она пустая, интервью по ТЗ проверять не из чего.

## 2. Целевая архитектура (маппинг на §3 спеки)

```
                      VDS (Ubuntu, systemd)
  ┌──────────────────────────────────────────────────────────────┐
  │  robin-runtime/ (код, отдельная рабочая директория)           │
  │                                                                │
  │  [Telegram Chat Adapter] ──DM/mention/voice──┐                 │
  │  [Scheduler: cron/timers] ──duties───────────┤                 │
  │                                              ▼                 │
  │                                   [Agent Runtime]              │
  │                                   Claude Agent SDK             │
  │                                   (сессии, промпт из soul.md)  │
  │        ┌──────────────┬───────────┴───────────┐               │
  │        ▼              ▼                        ▼               │
  │  [Tool Layer]   [Knowledge Mount]        [Memory]             │
  │  read-only:     ../team-brain (git,       learnings/          │
  │  - kb-search    read-only)                staged/ (write)     │
  │  - db-query?    soul.md, duties.md,       promoted/ (read)    │
  │  - voice STT    glossary, CLAUDE.md       state.md            │
  │        │                                                      │
  │        ▼                                                      │
  │  [Interaction Log] append-only (§7): ts, surface, user,      │
  │                    latency, success/error, trace link         │
  └──────────────────────────────────────────────────────────────┘
```

Топология (§3): Robin работает в **своей** директории, база знаний примонтирована **read-only** как соседний путь. Инструменты (поиск по репо, STT, запросы к данным) исполняются **вне** песочницы агента оркестратором — агент просит, оркестратор выполняет.

## 3. Дорожная карта по фазам

Порядок жёсткий: сначала база знаний и Q&A, затем обязанности. Каждая фаза самоценна и имеет приёмочный тест из §8 спеки.

### Фаза 0 — База знаний (предусловие, а не опция)
- Запустить `/init-team-os` → минимальный seed базы знаний (`CLAUDE.md` + 2–3 файла на главный повторяющийся вопрос команды).
- `/init-team-brain` → глоссарий и объектная модель из кода проекта + drift-checker.
- Наполнить `product/` реальным ТЗ/спецификациями проекта — **это фундамент для интервью по ТЗ** (без него нечего спрашивать).
- **Выход:** репо, отвечающее на реальный вопрос команды. **Тест M0:** свежая сессия агента отвечает на реальный вопрос из репо со ссылкой на файл-источник.

### Фаза 1 — Telegram Q&A (M0→M1)
- Chat Adapter (python-telegram-bot / aiogram): DM, mention в группе, логирование.
- Agent Runtime на Claude Agent SDK; системный промпт собирается из `soul.md` + конвенций.
- Инструмент `kb-search` (grep/поиск по примонтированному репо, read-only).
- Две универсальные конвенции (§4): цитировать источник; отвечать на языке спрашивающего.
- Context isolation (§6.5): свой workspace, без утечки личных конфигов оператора.
- Interaction Log + `/cost` + дневной бюджет и rate-limit на пользователя (§7).
- **Тест M1:** сотрудник (не разработчик) спрашивает в командном чате → получает ответ из репо со ссылкой.

### Фаза 2 — Голос (слот 21)
- Приём голосовых заметок Telegram → STT (Whisper API или локальный whisper.cpp на VDS).
- Транскрипт идёт в тот же конвейер, что и текст (§6.1: транскрибировать перед обработкой).
- Опц. TTS на ответ (по флагу пользователя), чтобы не платить за озвучку каждого ответа.
- **Тест:** голосовой вопрос онбордингу получает корректный ответ (текст + опц. аудио).

### Фаза 3 — Онбординг сотрудников (первая проектная обязанность)
Дизайн — см. §4.1. Реализуется как **скил в базе знаний** (`skills/onboarding/`) + указатель в runtime. Состояние прохождения — в SQLite. **Тест:** новый сотрудник проходит чек-лист онбординга, Robin ведёт его, отвечает из базы, фиксирует прогресс.

### Фаза 4 — Дайджест + Learning loop (M2→M4)
- Scheduler: ежедневный дайджест активности команды, персистится (§6.3 минимальный ростер).
- Дайджест = queryable память: «что я пропустил за неделю» отвечается из дайджестов.
- Learning loop (§6.4): негативный фидбэк → staged-файл → **обязательная проверка чтением после записи** (продакшн-урок: staged-записи молча не сохранялись неделями) → ручное промо.
- Негативные проверки (§7): алерт на устаревший state-файл, полнота листинга памяти, liveness (дайджест старше каденции + грейс → алерт).
- **Тест M4:** правка становится staged-файлом (проверенно сохранён), промотируется человеком, наблюдаемо меняет поздний ответ.

### Фаза 5 — Интервью по ТЗ/спецификациям
Дизайн — §4.2. **Тест:** Robin задаёт участнику вопросы по спеке проекта, оценивает ответы, выдаёт отчёт с пробелами и ссылками на источники в базе знаний.

### Фаза 6 — Интервью кандидатов
Дизайн — §4.3. Самая чувствительная роль (оценка людей, приватность). Идёт последней, после отладки механики интервью на ТЗ. **Destination follows sensitivity (§6.3):** результаты — приватным DM нанимающему, не в общий канал.

## 4. Дизайн трёх проектных обязанностей

Все три — **новые обязанности поверх спеки**. Каждая объявляется в `robin/duties.md` (§6.3: триггер, входы, выход, назначение, владелец) и/или реализуется скилом в базе знаний.

### 4.1 Онбординг сотрудников (первая)
- **Тип:** интерактивный DM-сценарий + чек-лист (состояние в SQLite).
- **Вход:** база знаний (product/, glossary, decisions), персональный чек-лист роли.
- **Поведение:** Robin ведёт новичка по этапам, отвечает на вопросы из репо, отмечает выполненное, эскалирует «нет в репо» вместо галлюцинации (§4).
- **Выход:** прогресс онбординга + список вопросов новичка, которых не было в базе → кандидаты в staged learning (пробелы базы знаний как сигнал).
- **Почему первой:** самый безопасный сценарий, ближе всего к M0/M1 (чистое grounded-Q&A + линейный сценарий), даёт быструю видимую ценность.

### 4.2 Интервью по ТЗ/спецификациям
- **Тип:** генеративное интервью с оценкой.
- **Вход:** спецификации проекта из базы знаний → Robin **генерирует вопросы из реального содержимого репо** (а не из общих знаний).
- **Механика оценки — критичная развилка (см. §7 рисков):** ответы оцениваются сверкой с источником в базе, не «мнением модели». Каждый вердикт — со ссылкой на файл-эталон. Оценка — черновик для человека, а не финальный балл.
- **Выход:** отчёт «знает / пробел / расходится со спекой» с цитатами источников.
- **Побочная ценность:** вопросы, на которые база сама не отвечает однозначно, = дефекты базы знаний.

### 4.3 Интервью кандидатов
- **Тип:** скрининг-интервью на соответствие требованиям проекта.
- **Вход:** требования роли (в базе знаний) + резюме/ответы кандидата.
- **Приватность (§6.3, §6.5):** данные кандидата — чувствительные; отчёт **приватным DM** нанимающему, дедупликация и исключение внутренних аккаунтов не нужны, но PII не логируется в общий interaction log в открытом виде.
- **Осторожно:** Robin даёт **структурированную сводку соответствия**, а не решение «нанимать/нет». Финальное решение — за человеком. Оценка людей моделью несёт риск предвзятости и ошибок — фиксируем это как явное ограничение.
- **Почему последней:** максимальный риск (люди, приватность, юридические аспекты), нужна отлаженная механика интервью из §4.2.

## 5. Хостинг на VDS

**Выбранная площадка: Contabo VPS** — 4 vCPU, 8 GB RAM, 75 GB NVMe + 150 GB SSD, 1 snapshot, порт 200 Mbit/s, unlimited traffic, регион EU, Ubuntu 24.04. С запасом покрывает нагрузку: инференс LLM на стороне Anthropic API, VPS только оркестрирует. 8 GB RAM / 4 ядра комфортно тянут и локальный whisper.cpp (сценарий B по STT), поэтому распознавание голоса можно позже увести с API на своё железо без апгрейда. NVMe — под бота/SQLite/`git pull` базы знаний; SSD — под бэкапы, транскрипты, аудио.

**Приём Telegram-апдейтов: long polling (на MVP).** Бот сам ходит на Telegram API исходящими запросами — **домен и SSL-сертификат не нужны**, входящие порты открывать не надо, работает за NAT. Переход на webhook (нужен публичный HTTPS + валидный TLS, проще всего домен + Caddy с авто-Let's Encrypt) откладываем — для Robin разница в задержке несущественна, а long polling убирает целый класс точек отказа.

- **ОС/процессы:** Ubuntu 24.04; бот — systemd-сервис с авто-рестартом; обязанности — systemd-timers (надёжнее пользовательского cron).
- **Секреты:** ENV-файл вне git / secret-manager (§6.5). Токены Telegram, API-ключ Anthropic, STT/TTS.
- **База знаний:** git-clone на VDS, `git pull` по расписанию (§4: быстро меняющиеся источники чаще, код реже — референс: hourly vs daily). Монтируется агенту read-only.
- **Liveness (§7 MUST):** внешний heartbeat/алерт, если дайджест не вышел вовремя. «Круглосуточно» на спящей машине падает молча.
- **Стоимость-контроль:** дневной бюджет + rate-limit на пользователя (§7). Без cap безнадзорный агент — это «liveness-чек наоборот».
- **Бэкапы:** SQLite (состояние интервью/онбординга) и `learnings/` в регулярный бэкап.

## 6. Ориентир по стоимости

- Референс: **$30–40/мес** при ~100 взаимодействий/мес на Opus-модели, без meeting-слоя.
- Доминируют выходные токены; grep по репо и транскриптам дёшев на входе.
- **Голос добавляет:** STT (Whisper API ~$0.006/мин или локальный whisper.cpp ~$0 сверх VDS) + опц. TTS. Локальный STT на VDS снижает переменную стоимость почти до нуля ценой CPU/RAM.
- **Строгое требование:** дневной cap кошелька обязателен до первого продакшн-запуска.

## 7. Риски и критические предупреждения (из шрамов спеки)

1. **«0 ошибок в логах» ≠ «0 сбоев» (§7).** Референс: 276 взаимодействий без ошибок при трёх невидимых сбоях (пагинация памяти прятала файлы, staged-записи не сохранялись, state 2+ недели протух). → Обязательны негативные проверки: read-back после записи, алерт на протухший state, проверка полноты листинга.
2. **Оценка людей/знаний моделью — главный проектный риск.** Интервью (ТЗ и кандидаты) выдают **черновик для человека со ссылками на эталон**, не автономный вердикт. Иначе получим уверенно неверные оценки и юридические риски по кандидатам.
3. **Экранирование вывода (§6.7).** Пользовательский текст в Telegram HTML/Markdown (`<`, `&`, `*`, `_`) ломает парсер → сообщение молча деградирует/пропадает. Экранировать до форматирования; отказ отправки = сбой для лога, не тихий фолбэк. Особенно актуально для интервью, где цитируются ответы людей.
4. **Голос — не воронка ложных срабатываний.** Никаких realtime voice-avatars (спека прямо отвергает для встреч). Голосовые заметки → STT → тот же текстовый конвейер.
5. **Chat как недоверенный вход (§6.5).** Инструкции из чата не должны менять конфиг/промотировать память/менять доступы — это ручные out-of-band действия.
6. **Приватность онбординга/интервью.** Команду уведомить о логируемых каналах (§6.5); данные кандидатов — приватным DM, не в общий канал (§6.3).
7. **База знаний — узкое место.** Пустая/протухшая база обесценивает все три обязанности. `tier:`/`last_reviewed` frontmatter + drift-checker из `/init-team-brain` — дешёвая страховка.

## 8. Ближайшие шаги (эта неделя)

1. **Запустить `/init-team-os`** в репозитории проекта → seed базы знаний + ответ на реальный вопрос команды (это и есть тест M0).
2. **Запустить `/robin-init`** → сгенерирует `soul.md`, `robin/duties.md`, `ROBIN-SPEC.local.md` и `KICKOFF.md` под наш стек (Python/Telegram/Claude Agent SDK/VDS). Это резолвит слоты из §1 в файлы, версионируемые в репо.
3. **Поднять VDS-скелет:** systemd-демон + Telegram-адаптер + `kb-search` → добить M1 (ответ в чате со ссылкой).
4. Наполнить `product/` реальным ТЗ проекта — фундамент для интервью по ТЗ.
5. Только после M1 — голос (фаза 2) и онбординг (фаза 3).

> Правило принятия решений: адаптация следует за доказанной ценностью, не за анонсом. Сначала один реальный ответ, который увидит коллега, — потом обязанности.
